## Два формата

### JSON (`.json`, Jackson)

```json
{
  "schema_version" : 1,
  "contacts" : [ {
    "type" : "corporate",
    "name" : "Игорь Лесной",
    "phone" : "+79130000003",
    "email" : "les@corp.local",
    "organization" : "ООО \"Альфа\"; филиал",
    "position" : "Инженер",
    "internal_number" : "204"
  } ]
}
```

- `schema_version` — версия схемы. Сейчас 1. Файл с другой версией не читается (`UNSUPPORTED_VERSION`).
  В лабе 4 на этом месте появятся миграции.
- `type` — `contact`, `emergency` или `corporate`. По нему восстанавливается нужный подкласс.
- `position` и `internal_number` пишутся только у corporate (`@JsonInclude(NON_NULL)`).
- Лишние поля игнорируются (так новые версии программы могут добавлять поля).

### Свой бинарный формат (`.ctb`)

| Смещение | Размер | Что |
|---|---|---|
| 0 | 4 | сигнатура `43 54 4B 42` («CTKB») |
| 4 | 2 | версия формата (сейчас 1) |
| 6 | 4 | число записей N |
| 10 | … | N записей |

Запись: 1 байт типа (1 — contact, 2 — emergency, 3 — corporate), затем строки name, phone, email,
organization, у corporate ещё position и internal_number. Строка — 2 байта длины в байтах и сами
байты в UTF-8 (длина −1 означает null, максимум 4096 байт). Все числа big-endian
(так пишет `DataOutputStream`).

## Ошибки чтения

Любая проблема с содержимым файла — это `SerializationException` с кодом (`getError()`) и местом
(`getLocation()`): для JSON путь вида `$.contacts[3].name` или «строка 5, столбец 12», для бинарного
«запись 2, байт 118». Если файла нет или нет прав, летит обычный `IOException`, это другая ситуация.

| Код | Когда |
|---|---|
| `EMPTY_FILE` | файл пустой |
| `MALFORMED` | сломанный JSON, `contacts` не массив, запись не объект |
| `MISSING_FIELD` | нет `schema_version`, `contacts`, `type` или `name` |
| `INVALID_VALUE` | пустое имя, буквы во внутреннем номере, поле не того типа |
| `UNKNOWN_TYPE` | неизвестный `type` / код типа |
| `DUPLICATE_KEY` | два контакта с одинаковым именем (без учёта регистра) |
| `BAD_MAGIC` | у бинарного файла чужая сигнатура (например, открыли JSON как `.ctb`) |
| `UNSUPPORTED_VERSION` | версия схемы/формата не 1 |
| `TRUNCATED` | бинарный файл обрывается посередине |
| `CORRUPTED` | отрицательное число записей, недопустимая длина строки, лишние байты в конце |

## Сравнение форматов (10 000 контактов, среднее по 5 прогонам после 2 прогревочных)

Замер на облачной машине, у себя запустите `FormatComparison` и вставьте свои числа в отчёт.

| Формат | Размер | Запись | Чтение |
|---|---|---|---|
| CSV | 1 201 699 Б | 23,8 мс | 44,0 мс |
| JSON (с отступами) | 2 347 990 Б | 21,2 мс | 52,9 мс |
| Бинарный | 1 171 600 Б | 12,7 мс | 21,3 мс |

- JSON самый большой: имя каждого поля повторяется в каждой записи, плюс отступы. Зато его можно
  открыть в блокноте и понять без документации, и к нему легко добавлять поля.
- Бинарный самый компактный и быстрый: нет имён полей и разбора текста, длина строки известна заранее.
  Но без описания формата файл не прочитать, и любая правка формата требует новой версии.
- Чтение в обоих случаях включает проверку и вставку в Trie, поэтому оно дольше записи.

## Что показывать на защите

1. **Сравнение.** Запустить `FormatComparison`, показать таблицу, начало JSON и hex-дамп:
   первые 4 байта `CTKB`, потом `00 01` (версия), `00 00 27 10` (10000 записей).
2. **Тесты.** Запустить все тесты, открыть `FixtureTest`: каждый испорченный файл даёт свой код
   ошибки. Показать пару фикстур в `src/test/resources/fixtures` (например, `broken.json`, `truncated.ctb`).
3. **Round-trip.** `RoundTripTest`: контакты с кавычками, `;`, обратным слешем, эмодзи и пустыми полями
   сохраняются и читаются обратно без изменений, типы (Emergency, Corporate) сохраняются.
4. **Атомарная запись.** `FileStorage.save` пишет во временный файл рядом и потом переименовывает
   его поверх старого. Если запись упадёт посередине, старый файл останется целым.
5. **Код.** `Serializer<T>` — общий интерфейс, `ContactFormat` — реестр (формат по расширению),
   `ContactMapper.fromDto` — одна проверка данных для обоих форматов.

## Ключевые решения

- **Один интерфейс `Serializer<T>`, две реализации.** Остальной код (`FileStorage`, задачи, UI) не знает,
  какой формат внутри. Новый формат = новый класс + строчка в `ContactFormat`.
- **DTO отдельно от модели.** Jackson работает с record'ами `ContactDto`/`ContactBookDto`, а не с
  `Contact` напрямую. Модель не обвешана аннотациями Jackson, имена полей в файле (`internal_number`)
  не зависят от имён в Java, конструкторы модели не нужно открывать для рефлексии.
- **Массивы, а не List.** DTO хранит `ContactDto[]`, сериализатор возвращает `Contact[]` — как и всё
  хранилище из лабы 2.
- **Проверка в одном месте.** И JSON, и бинарный формат превращают запись в `ContactDto` и зовут
  `ContactMapper.fromDto`. Поэтому правила (имя не пустое, номер из цифр, тип известен) одинаковые.
- **Сначала дерево JSON, потом объекты.** `readTree` → проверка `schema_version` → разбор записей
  по одной. Так ошибка версии видна раньше, чем Jackson споткнётся о новые поля, а в сообщении
  есть номер записи.
- **Импорт идёт в новое хранилище** (как загрузка CSV в лабе 2). Если файл битый, текущие данные
  в окне не трогаются.
- **Сигнатура и версия в бинарном файле.** По сигнатуре сразу видно «это не наш файл», по версии —
  «файл от новой программы». Без них чужой файл читался бы как мусорные длины строк.
- **Ограничения на длины** (`MAX_STRING_BYTES`, `MAX_COUNT`). Испорченный файл не заставит
  программу выделить гигабайты памяти под «строку длиной 2 миллиарда».
