## Окно программы

- **Панель кнопок сверху:** Загрузить CSV, Сохранить CSV, Добавить, Изменить, Удалить, поле «Кол-во»,
  Сгенерировать, Очистить.
- **Слева:** поле поиска по полному имени и таблица контактов, отсортированная по алфавиту
  (это порядок обхода дерева).
- **Справа:**
  - поле «Префикс» — автодополнение: список подходящих контактов и надпись «Контактов в поддереве: N»;
  - «Глубина» — сколько уровней дерева рисовать;
  - холст с деревом и легенда под ним.
- **Снизу:** строка состояния, число контактов и узлов, полоса прогресса и кнопка «Отмена».

### Как нарисовано дерево

Дерево рисуется слева направо. Корень слева, каждый следующий столбец — следующая буква имени,
поэтому ветки читаются как слова.

- белый кружок — промежуточный узел;
- зелёный кружок — здесь заканчивается имя, в узле лежит контакт;
- оранжевая обводка и оранжевые рёбра — путь к ключу последней операции (добавление,
  изменение, удаление, поиск, клик по строке таблицы, ввод префикса);
- число над узлом — `subtreeSize`, сколько контактов в поддереве;
- `…` справа от узла — у узла есть дети, которые не поместились в рисунок;
- `␣` — пробел между фамилией и именем.

Если в поле «Префикс» что-то введено, рисуется только поддерево этого префикса. За один раз
рисуется не больше 200 узлов (`MAX_VISIBLE_NODES`). Узлы отбираются обходом в ширину, поэтому
сначала видны верхние уровни. На 10⁵ контактов всё дерево нарисовать нельзя (около 800 тысяч
узлов), поэтому смотреть его нужно по префиксу.

## Что показывать на защите

1. **Загрузка.** «Загрузить CSV» → `test.csv`. Появляется окно «Часть строк пропущена»
   с номером строки и кодом ошибки (`UNKNOWN_TYPE`). В таблице 4 контакта, справа их дерево.
2. **Добавление.** «Добавить» → «Иван Сидоров». Путь новой ветки подсвечен оранжевым, ветка
   отходит от общей части «ив…». Если ещё раз добавить «иван сидоров», будет ошибка «уже есть».
   Если переименовать корпоративный контакт в уже занятое имя — тоже «уже есть», а не просто
   «не получилось».
3. **Валидация.** В диалоге оставить имя пустым или вписать буквы во внутренний номер
   корпоративного контакта. Окно не закроется, появится список ошибок (`Editable.validate()`).
4. **Read-only.** Выбрать «Служба спасения» (Emergency): кнопка «Изменить» серая.
   Для Corporate она активна. Тип в диалоге редактирования заблокирован.
5. **Поиск.** Ввести полное имя → «Найти»: строка выделяется в таблице, путь подсвечен.
   Для несуществующего имени подсвечивается та часть пути, которую успели пройти.
6. **Автодополнение и подсчёт.** В поле «Префикс» ввести `и`, потом `ив`: список и число
   «Контактов в поддереве» меняются на каждую букву, на холсте остаётся только поддерево.
7. **Удаление.** «Удалить» → ветка исчезает, общая часть с другими именами остаётся,
   числа в узлах уменьшаются.
8. **Генерация с прогрессом и отменой.** В поле «Кол-во» указать 1 000 000 →
   «Сгенерировать» → во время работы нажать «Отмена». В строке состояния будет
   «Генерация остановлена, добавлено N из 1000000», и эти N контактов останутся (число
   точное, счётчик «Контактов» внизу вырос ровно на N). Потом сгенерировать 10 000 и
   посмотреть дерево по префиксу `иванов`.
9. **Фоновая загрузка большого файла.** Сохранить 10⁵ контактов в CSV, затем загрузить этот файл:
   полоса прогресса идёт (по байтам файла), окно не зависает. Если отменить загрузку, старые
   данные остаются.
10. **Консоль.** `RaceDemo`: без синхронизации `size()` меньше 160 000 и часть вставок падает
    с исключением, с `TrieStore` («С ReadWriteLock») — ровно 160 000. `Benchmark` — таблица
    для отчёта.

## Ключевые решения

### Структура (`Trie<V>`)

- **Дети узла.** Хранятся в двух массивах `char[] symbols` и `Node<V>[] children`, отсортированных
  по символу. Ребёнок ищется бинарным поиском, при заполнении массив увеличивается вдвое
  (`System.arraycopy`). Коллекций из java.util внутри нет.
  - Почему не массив на 33 буквы: в именах есть кириллица, латиница, цифры и пробел, массив
    на весь алфавит в каждом узле съел бы много памяти.
  - Почему не связный список детей: сортированный массив даёт поиск за O(log σ) и сразу
    алфавитный порядок при обходе.
- **`subtreeSize` в каждом узле.** При вставке и удалении счётчики обновляются на пути до корня
  (по ссылке `parent`). Поэтому «подсчёт контактов в поддереве» — это спуск по префиксу и чтение
  одного числа, без обхода.
- **Удаление.** После удаления значения ветка срезается снизу вверх, пока узел пустой и без детей.
- **Ключ.** Имя после `trim()` и `toLowerCase(Locale.ROOT)`. «Иван» и «иван» — один ключ.
  Дубликаты запрещены: `add` бросает `DuplicateKeyException`, `tryAdd` возвращает `false`,
  загрузчик CSV даёт ошибку `DUPLICATE_NAME`.
- **Изменение.** `update(староеИмя, новыйКонтакт)` бросает `KeyNotFoundException`, если старого
  контакта нет, и `DuplicateKeyException`, если новое имя занято.
- **Модель неизменяемая.** Поля контактов `final`, сеттеров нет. Переименование —
  `withName(новоеИмя)`, он возвращает копию того же типа. Есть `equals`/`hashCode`.
- **Подсветка.** Поиск и автодополнение ничего не пишут в дерево. Тот, кто рисует, передаёт
  ключ последней операции в `snapshot(prefix, maxDepth, maxNodes, highlightKey)`, и узел
  подсвечивается, если этот ключ начинается с префикса узла.
- **Снимок для рисования (`TrieNodeView`).** Неизменяемый record. GUI не видит внутренние узлы
  и не может испортить дерево. Снимок ограничен по глубине и числу узлов: внутренний класс
  `SnapshotBuilder` обходит дерево в ширину в параллельные массивы и собирает узлы с конца.
  Перерисовка занимает пару миллисекунд даже на 10⁵ записей.
- **Дженерики.**
  - `Trie<V>` — значение любого типа, узел тоже обобщённый (`Node<V>`), приведений нет.
  - `TrieStore<T>` получает функцию ключа (`Contact::getName`) и фабрику массива
    (`Contact[]::new`): с дженериками нельзя написать `new T[n]`, а результаты возвращаются
    массивом, не списком.
  - `ContactStores.create()` собирает хранилище для контактов.
- **Потоки.** Сам `Trie` не потокобезопасен. `TrieStore` защищён `ReentrantReadWriteLock`:
  чтения идут параллельно, запись — одна и без читателей. `RaceDemo` показывает, что без
  этого ломается.
- **CSV.** Разделитель `;`, поля с `;` или `"` берутся в кавычки (`CsvFormat`). Прогресс
  загрузки — в байтах, файл читается один раз.

### GUI

- **Разделение по классам, чтобы не было god object:**
  - `MainApp` — компоновка и обработчики кнопок;
  - `ContactTable` — колонки таблицы;
  - `ContactDialog` — форма;
  - `TriePane` — раскладка и рисование дерева;
  - `BackgroundRunner` — запуск задач на одном рабочем потоке (`ExecutorService`), прогресс,
    отмена, блокировка кнопок;
  - `Alerts` — диалоги.
- **Таблица — только отображение.** Данные лежат в `TrieStore`, после каждой операции таблица
  заполняется заново из `store.toArray()`.
- **Долгие операции не блокируют FX-поток.** Загрузка, сохранение и генерация идут в
  `javafx.concurrent.Task` на отдельном потоке-демоне; при закрытии окна `MainApp.stop()`
  вызывает `runner.shutdown()`:
  - прогресс привязан через `progressProperty()`;
  - отмена загрузки и сохранения — `cancel()`, генерации — `requestStop()` (`StoppableTask`),
    тогда задача завершается нормально и возвращает точное число добавленных;
  - результат обрабатывается в `setOnSucceeded`, `setOnCancelled` и `setOnFailed`, которые
    выполняются в FX-потоке;
  - пока задача идёт, кнопки, меняющие данные, заблокированы (`disableProperty().bind(busy)`).
- **Загрузка CSV идёт в новое хранилище.** Подмена происходит только после успеха. Таблица не
  видит наполовину загруженные данные, при отмене или ошибке старые данные остаются.
- **Генерация пишет прямо в текущее хранилище.** Поэтому после остановки уже созданные записи
  остаются, это видно в таблице.
- **Редактирование не меняет объект в дереве.** Контакты неизменяемые, диалог создаёт новый
  объект, а `store.update(староеИмя, новый)` переносит его. GUI ловит `DuplicateKeyException`
  («уже есть») и `KeyNotFoundException` («уже удалён») по отдельности.
- **Валидация в диалоге.** Сделана фильтром на кнопке «Сохранить» (`addEventFilter` +
  `event.consume()`): при ошибке окно не закрывается и введённое не теряется.
- **Подсветка через `lastKey`.** `MainApp` помнит ключ последней операции (добавление,
  изменение, удаление, поиск, выбор строки, ввод префикса) и передаёт его в `snapshot`.
  Поэтому порядок вызовов в `refresh()` больше не важен: автодополнение подсветку не сбивает.

## Асимптотика

L — длина ключа, P — длина префикса, σ — число детей у узла, k — сколько вернуть, m — узлы, пройденные в поддереве, n — контактов.

| Операция | Сложность | Обоснование |
|---|---|---|
| вставка | O(L·log σ) | спуск по L символам, на каждом бинарный поиск ребёнка; вставка в массив детей O(σ), σ маленькое |
| поиск | O(L·log σ) | тот же спуск |
| удаление | O(L·log σ) | спуск, затем подъём по `parent` с уменьшением счётчиков и срезкой пустых узлов |
| автодополнение (k штук) | O(P·log σ + m) | спуск к узлу префикса, затем обход в глубину, пока не набрано k |
| подсчёт в поддереве | O(P·log σ) | спуск к узлу префикса, ответ уже лежит в `subtreeSize` |
| toArray | O(число узлов) | обход в глубину, дети отсортированы → алфавитный порядок |
| снимок для рисования | O(K·D), K = min(узлов в поддереве, лимит), D — глубина | обход в ширину до лимита глубины и числа узлов; для каждого узла строится префикс |
| загрузка CSV | O(размер файла) | один проход, прогресс по байтам |
| память | O(сумма длин ключей) | в худшем случае один узел на символ |

## Возможные вопросы

- **Почему Trie медленнее TreeMap на вставке и поиске?** TreeMap делает около log₂n ≈ 17
  сравнений строк. Trie делает спуск на каждый символ имени (около 25) с бинарным поиском в
  каждом узле и создаёт много мелких объектов. Зато подсчёт по префиксу у Trie O(P), а у TreeMap
  `subMap(...).size()` проходит все элементы диапазона. На 10⁵ это 0,08 мс против 310 мс.
- **Где здесь гонка?** В `Node.addChild` два потока одновременно сдвигают массив детей и
  увеличивают `childCount`. Один ребёнок затирается или индекс выходит за массив. Счётчики
  `subtreeSize++` тоже теряют обновления, это не атомарная операция.
- **Зачем блокировка на чтении, если чтение ничего не меняет?** Чтение идёт по массивам, которые
  может в этот момент сдвигать запись. Блокировка чтения не пускает писателя, но не мешает
  другим читателям.
- **Почему в первой версии был `synchronized`, а теперь `ReadWriteLock`?** Раньше поиск записывал
  `stamp` в узлы для подсветки, то есть тоже писал, и два «читателя» гонялись бы. Теперь чтение
  чистое, и читатели могут работать одновременно.
- **Почему возвращаются массивы, а не List?** По заданию списки нельзя использовать как
  хранилище. Массив — простой результат фиксированной длины, его длина известна заранее
  (`min(limit, subtreeSize)`).

## Что исправлено после первой версии

1. **CSV с `;` внутри полей.** Раньше строка резалась простым `split(";")`, и организация вида
   «ООО Рога; Копыта» ломала файл. Теперь `CsvFormat` понимает кавычки (как RFC 4180, но с `;`),
   при сохранении такие поля берутся в кавычки, а сломанные кавычки дают код `BAD_QUOTES`.
2. **Разные ошибки у `add` и `update`.** Раньше оба возвращали `boolean`, и GUI не знал причину.
   Теперь `add` бросает `DuplicateKeyException`, `update` — `KeyNotFoundException` или
   `DuplicateKeyException`, и пользователь видит правильное сообщение. Для массовых операций
   есть `tryAdd`.
3. **Поиск без побочных эффектов и `ReadWriteLock`.** Раньше поиск и автодополнение писали в
   узлы счётчик `stamp` для подсветки, поэтому любое чтение требовало эксклюзивной блокировки.
   Теперь подсветка передаётся в `snapshot` ключом, чтение ничего не меняет, и в `TrieStore`
   стоит `ReentrantReadWriteLock`: читатели работают параллельно.
4. **Обобщённый узел `Node<V>`.** Раньше значение лежало в `Object` и приводилось к `V` при
   каждом чтении. Теперь типы проверяет компилятор.
5. **Прогресс загрузки по байтам.** Раньше файл читался дважды: сначала считались строки, потом
   разбор. Теперь `CountingInputStream` считает прочитанные байты, общий объём берётся из
   `Files.size`, и файл читается один раз.
6. **Точное число при отмене генерации.** Раньше после `Task.cancel()` число добавленных
   считалось как разница размеров, пока фоновый поток ещё мог вставлять, — результат был
   неточным. Теперь генерация — `StoppableTask`: «Отмена» ставит флаг, задача сама выходит из
   цикла и возвращает `GenerationResult` с точным числом.
