# Гайд по фронтенду (JavaFX), лабораторная 2

Этот файл можно читать двумя способами:

- разделы 1–10 объясняют, как устроен готовый GUI (для защиты);
- раздел 11 — короткий справочник для того, кто пишет или дописывает фронт: какие методы
  бэкенда вызывать, какие исключения ловить, как запускать долгие операции и как получить
  подсветку.

Номера строк указаны для текущей версии кода.

## 1. Какие файлы относятся к фронту

Весь GUI лежит в пакете `org.example.ui` (`src/main/java/org/example/ui`).

| Файл | Строк | За что отвечает |
|---|---|---|
| `MainApp.java` | 397 | Главное окно: компоновка, обработчики кнопок, связь с хранилищем, `lastKey` |
| `TriePane.java` | 162 | Визуализация дерева на `Canvas`: раскладка узлов и отрисовка |
| `ContactDialog.java` | 130 | Диалог «Добавить / Изменить» с валидацией |
| `ContactTable.java` | 50 | Таблица контактов (колонки, выделение строки) |
| `BackgroundRunner.java` | 83 | Запуск фоновых задач на одном рабочем потоке: прогресс, отмена/остановка, блокировка кнопок |
| `Alerts.java` | 59 | Готовые диалоги: ошибка, предупреждение, подтверждение |

Все классы, кроме `MainApp`, объявлены без `public`: они нужны только внутри пакета `ui`.

Кроме пакета `ui`, фронт пользуется:

| Файл | Зачем фронту |
|---|---|
| `org/example/Main.java` | Точка входа, запускает `ui.MainApp` |
| `module-info.java` | `exports org.example.ui`: без него JavaFX не сможет создать окно |
| `tasks/LoadCsvTask.java` | Фоновая загрузка CSV (`Task<LoadResult>`) |
| `tasks/SaveCsvTask.java` | Фоновое сохранение CSV (`Task<Integer>`) |
| `tasks/GenerateContactsTask.java` | Фоновая генерация (`StoppableTask<GenerationResult>`) |
| `tasks/StoppableTask.java`, `tasks/GenerationResult.java` | Мягкая остановка генерации и её точный итог |
| `store/TrieStore.java` | Хранилище и `snapshot(prefix, maxDepth, maxNodes, highlightKey)` для рисования |
| `store/DuplicateKeyException.java`, `store/KeyNotFoundException.java` | Ошибки `add` и `update`, которые ловит GUI |

## 2. Как классы связаны

```
Main ──launch──► MainApp
                   │
                   ├── ContactTable      (показывает rows)
                   ├── TriePane          (рисует TrieNodeView)
                   ├── ContactDialog     (возвращает новый Contact)
                   ├── BackgroundRunner  (запускает задачи на рабочем потоке)
                   ├── Alerts            (сообщения)
                   │
                   ├── String lastKey    ◄── ключ последней операции, для подсветки
                   └── TrieStore<Contact> store   ◄── единственное хранилище данных
                          ▲
            LoadCsvTask / SaveCsvTask / GenerateContactsTask (в фоне)
```

Главное правило: данные хранятся только в `TrieStore`.

- `rows` — это `ObservableList` для `TableView`. Это просто копия для показа, после каждой
  операции он заполняется заново из `store.toArray()`.
- `suggestions` — такая же копия для списка автодополнения.

Так что список здесь не хранилище, а то, что JavaFX требует для таблицы.

## 4. MainApp: что происходит при запуске и закрытии

`start(Stage)` (строки 75–107):

1. создаёт `BackgroundRunner`, `ContactTable` и `TriePane`;
2. собирает окно из `build*()`-методов;
3. вешает три слушателя (строки 90–101):
   - выбор строки таблицы: `lastKey = selected.getName()` и перерисовка, чтобы путь к
     контакту подсветился;
   - изменение текста в поле «Префикс»: `lastKey = newValue`, обновить автодополнение и
     перерисовать поддерево;
   - изменение «Глубины»: перерисовать;
4. показывает окно и вызывает `refresh("Готово")`.

`stop()` (строки 109–112) JavaFX вызывает при закрытии окна. Там `runner.shutdown()`:
текущая задача останавливается, рабочий поток завершается.

Константы вынесены в начало класса (строки 48–54), «магических чисел» в коде нет:

```java
private static final int SUGGESTION_LIMIT = 50;      // сколько подсказок показывать
private static final int MAX_VISIBLE_NODES = 200;    // сколько узлов рисовать
private static final int DEFAULT_DEPTH = 25;
private static final int MAX_DEPTH = 60;
private static final int MAX_GENERATE = 1_000_000;
private static final int MAX_ERRORS_SHOWN = 30;      // строк ошибок CSV в диалоге
private static final String DEFAULT_GENERATE = "1000";
```

Поля состояния (строки 56–64): `store`, `rows`, `suggestions`, `stage`, `table`, `triePane`,
`runner` и `lastKey`.

## 5. Каждая кнопка: что вызывается

| Кнопка | Метод (строки) | Что делает | Вызов хранилища | Что ловим |
|---|---|---|---|---|
| Загрузить CSV | `onLoad()` (231–248) | FileChooser → `LoadCsvTask` в **новый** store → при успехе `store = loaded`, `lastKey = null` → диалог пропущенных строк | `ContactStores.create()`, внутри задачи `tryAdd()` | ошибки задачи показывает `BackgroundRunner` |
| Сохранить CSV | `onSave()` (266–280) | пустой справочник → ошибка; FileChooser → `SaveCsvTask` в фоне | `size()`, внутри задачи `toArray()` | то же |
| Добавить | `onAdd()` (282–294) | `ContactDialog(null)` → `store.add(c)` | `add` | `DuplicateKeyException` → «уже есть» |
| Изменить | `onEdit()` (296–316) | `ContactDialog(selected)` → `store.update(староеИмя, новый)` | `update` | `DuplicateKeyException` → «уже есть», `KeyNotFoundException` → «уже удалён» |
| Удалить | `onDelete()` (318–326) | подтверждение → удаление | `removeByKey` | — |
| Найти | `onFind()` (328–343) | поиск по полному имени, выделение строки, подсветка пути | `findByKey` | — (не найден = `null`) |
| Сгенерировать | `onGenerate()` (345–362) | проверка числа 1…1 000 000 → `GenerateContactsTask` в **текущий** store | внутри задачи `tryAdd()` | `NumberFormatException` при разборе поля |
| Очистить | `onClear()` (364–370) | подтверждение → очистка, `lastKey = null` | `clear` | — |
| Отмена | `runner.cancel()` (строка 217) | генерация: `requestStop()`; загрузка/сохранение: `cancel()` | — | — |
| Поле «Префикс» | слушатель (96–100) | автодополнение + подсчёт + поддерево на холсте | `findByPrefix`, `countByPrefix`, `snapshot` | — |

Добавление и редактирование (строки 282–316):

```java
private void onAdd() {
    new ContactDialog(null).showAndWait().ifPresent(contact -> {
        try {
            store.add(contact);
        } catch (DuplicateKeyException e) {
            Alerts.error("Контакт с именем «" + e.getKey() + "» уже есть.");
            return;
        }
        lastKey = contact.getName();
        refresh("Добавлен: " + contact.getName());
        table.selectAndShow(contact);
    });
}
```

```java
try {
    store.update(selected.getName(), updated);
} catch (DuplicateKeyException e) {
    Alerts.error("Контакт с именем «" + e.getKey() + "» уже есть.");
    return;
} catch (KeyNotFoundException e) {
    Alerts.error("Контакт «" + e.getKey() + "» уже удалён.");
    refresh("Таблица обновлена");
    return;
}
```

Почему два разных `catch`, а не одна проверка `if (!store.update(...))`, как было в первой
версии: `update` может не получиться по двум разным причинам, и пользователю надо сказать,
по какой. При `KeyNotFoundException` таблица ещё и перерисовывается, чтобы убрать
устаревшую строку. В нашем окне контакт почти невозможно удалить «из-под» диалога, но
контракт хранилища это допускает (в лабе 5 будет несколько клиентов сразу).

После каждой операции вызывается `refresh(status)` (строки 372–378):

```java
private void refresh(String status) {
    redrawTrie();
    rows.setAll(store.toArray());
    updateSuggestions();
    sizeLabel.setText("Контактов: " + store.size() + ", узлов: " + store.nodeCount());
    statusLabel.setText(status);
}
```

Порядок вызовов здесь не важен. В первой версии автодополнение при обходе дерева
перезаписывало пометки подсветки, и перерисовку нужно было делать строго первой. Теперь
чтения из хранилища ничего не меняют, а что подсвечивать, определяет только `lastKey`
(раздел 9).

### 5.1. `lastKey` — ключ последней операции

Поле `private String lastKey` (строка 64). Его передают в снимок дерева, и на холсте
подсвечивается путь к этому ключу. Где оно меняется:

| Действие | Строка | Значение |
|---|---|---|
| Выбор строки в таблице | 92 | имя выбранного контакта |
| Ввод в поле «Префикс» | 97 | текст поля |
| Добавление | 290 | имя добавленного |
| Изменение | 312 | новое имя |
| Удаление | 324 | имя удалённого (подсветится оставшаяся общая часть пути) |
| Поиск | 333 | введённое имя (если не найдено — подсветится часть пути, которая есть) |
| Загрузка CSV | 240 | `null` (подсветки нет) |
| Очистка | 367 | `null` |

### Блокировка кнопок

Используются привязки (bindings), а не ручные `setDisable` в каждом обработчике
(строки 132–139):

```java
var busy = runner.busyProperty();
var selected = table.getSelectionModel().selectedItemProperty();
for (Button b : new Button[]{load, save, add, generate, clear}) {
    b.disableProperty().bind(busy);
}
edit.disableProperty().bind(busy.or(Bindings.createBooleanBinding(
        () -> !(selected.get() instanceof Editable), selected)));
delete.disableProperty().bind(busy.or(selected.isNull()));
```

Кнопка «Изменить» серая, если ничего не выбрано или выбран не-`Editable` контакт
(Emergency или базовый Contact). Это требование лабы 1.

Поиск, поле префикса и клик по таблице во время фоновой задачи **не** блокируются: это
чтение, и оно может идти параллельно с записью в хранилище (раздел 6).

## 6. BackgroundRunner: фоновые операции

Требование: GUI-поток не блокируется дольше 100 мс. Загрузка, сохранение и генерация 10⁵
записей длятся дольше, поэтому они идут в `javafx.concurrent.Task` на отдельном потоке.

### 6.1. Один рабочий поток

```java
private final ExecutorService executor = Executors.newSingleThreadExecutor(task -> {
    Thread thread = new Thread(task, "contacts-worker");     // BackgroundRunner.java, строки 20–24
    thread.setDaemon(true);
    return thread;
});
```

- **`ExecutorService` с одним потоком** вместо `new Thread(...)` на каждую задачу. Поток
  создаётся один раз и переиспользуется. Задачи выполняются строго по очереди: следующая
  начнётся только после того, как предыдущая действительно закончилась (даже если её
  отменили и GUI уже разблокировался, а поток дочитывает последнюю строку файла).
- **Поток-демон** не держит программу после закрытия окна.
- **`shutdown()`** (строки 71–74) вызывается из `MainApp.stop()`: останавливает текущую задачу
  и `executor.shutdownNow()`.

### 6.2. Запуск задачи

```java
<T> void run(Task<T> task, Consumer<T> onSuccess, Runnable onCancel) {   // строки 36–61
    if (busy.get()) {
        return;
    }
    current = task;
    busy.set(true);
    progressBar.progressProperty().bind(task.progressProperty());
    statusLabel.textProperty().bind(task.messageProperty());

    task.setOnSucceeded(e -> {
        finish();
        onSuccess.accept(task.getValue());
    });
    task.setOnCancelled(e -> {
        finish();
        onCancel.run();
    });
    task.setOnFailed(e -> {
        finish();
        Throwable error = task.getException();
        statusLabel.setText("Ошибка");
        Alerts.error(error == null ? "Неизвестная ошибка" : error.getMessage());
    });

    executor.execute(task);
}
```

- Пока идёт задача, вторую запустить нельзя (`if (busy.get()) return`).
- `call()` задачи выполняется в фоновом потоке. Задача сообщает прогресс через
  `updateProgress`, текст — через `updateMessage`; полоса и строка состояния привязаны к ним
  и обновляются сами.
- `setOnSucceeded`, `setOnCancelled` и `setOnFailed` JavaFX вызывает уже в FX-потоке, поэтому
  в них можно трогать таблицу и холст.
- `finish()` (строки 76–82) снимает привязки, обнуляет прогресс, забывает `current` и ставит
  `busy = false`, после чего кнопки разблокируются сами.

### 6.3. Отмена: две разные кнопки под одним названием

```java
void cancel() {                                              // строки 63–69
    if (current instanceof StoppableTask<?> stoppable) {
        stoppable.requestStop();
    } else if (current != null) {
        current.cancel();
    }
}
```

| Задача | Что делает «Отмена» | Чем заканчивается задача | Что видит пользователь |
|---|---|---|---|
| Генерация (`StoppableTask`) | `requestStop()` — ставит флаг | **нормально**, `onSucceeded` с `GenerationResult` | «Генерация остановлена, добавлено N из M», N точное |
| Загрузка / сохранение | `Task.cancel()` | `onCancelled` | «Загрузка отменена, данные не изменились» |

**Почему генерация останавливается мягко.** Генерация пишет прямо в рабочее хранилище, и
надо честно сказать, сколько контактов осталось. В первой версии после `cancel()` число
считалось в `onCancelled` как `store.size() - before`. Но `onCancelled` вызывается сразу после
`cancel()`, а фоновый поток в этот момент ещё может вставлять контакт — число было неточным
(гонка). Теперь фоновый поток сам выходит из цикла и возвращает точное `added`:

```java
runner.run(new GenerateContactsTask(store, count),          // MainApp.java, строки 357–361
        result -> refresh(result.stopped()
                ? "Генерация остановлена, добавлено " + result.added() + " из " + result.requested()
                : "Сгенерировано " + result.added()),
        () -> refresh("Генерация отменена"));
```

Ветка `onCancel` у генерации остаётся на всякий случай (например, если задачу отменят
через `cancel()` при закрытии окна).

**Почему загрузку можно отменять жёстко.** Она пишет в отдельное новое хранилище. При отмене
его просто выбрасывают, точное число загруженных строк никому не нужно.

**Почему загрузка идёт в новый store, а генерация в текущий:**

- Загрузка в новое хранилище: пока файл читается, таблица видит старые данные. При отмене или
  ошибке ничего не теряется. Хранилище подменяется одной строкой (`store = loaded`) только
  после успеха.
- Генерация дописывает в текущее хранилище, поэтому после остановки уже созданные записи
  остаются, и в статусе видно, сколько их.

Пока фоновый поток пишет в `store`, FX-поток может читать его (клик по строке, ввод
префикса). Это безопасно: в `TrieStore` стоит `ReentrantReadWriteLock`. Каждая вставка
берёт блокировку записи на микросекунды, чтение ждёт только её, а не всю генерацию.

## 7. ContactDialog: добавление и редактирование

- `new ContactDialog(null)` — добавление. Можно выбрать тип «Контакт» или «Корпоративный
  контакт». Аварийный (read-only) тип выбрать нельзя: он появляется только из файла.
- `new ContactDialog(existing)` — редактирование. Поля заполнены (`fill`, строки 77–88), тип
  заблокирован.
- Поля «Должность» и «Внутр. номер» видны только у корпоративного типа (`setVisible` +
  `setManaged`, строки 94–103).

**Диалог не меняет исходный объект, а создаёт новый** (`buildContact()`, строки 105–115).
Контакты неизменяемые: сеттеров нет, все поля `final`, поменять объект нельзя в принципе.
`MainApp` вызывает `store.update(староеИмя, новыйОбъект)`, и хранилище само переносит контакт
под новый ключ. Если бы имя можно было поменять прямо у объекта в дереве, контакт остался бы
лежать под старым ключом и перестал бы находиться — неизменяемость это исключает.

**Валидация** сделана фильтром на кнопке «Сохранить» (строки 65–72):

```java
Button saveButton = (Button) getDialogPane().lookupButton(saveType);
saveButton.addEventFilter(ActionEvent.ACTION, event -> {
    List<String> errors = validate(buildContact());
    if (!errors.isEmpty()) {
        Alerts.warning("Некорректные данные", String.join("\n", errors));
        event.consume();
    }
});
```

`event.consume()` не даёт диалогу закрыться, и введённое не теряется.

Для `Editable`-типов вызывается `validate()` из модели (лаба 1), для обычного контакта
проверяется только непустое имя (`validate`, строки 117–122).

## 8. ContactTable

Наследник `TableView<Contact>`. Колонки создаются одним методом
`column(название, ширина, геттер)` (строки 39–45):

```java
getColumns().add(column("Имя", 220, Contact::getName));
getColumns().add(column("Должность", 110,
        c -> c instanceof CorporateContact cc ? cc.getPosition() : ""));
```

Используются лямбды, а не `PropertyValueFactory`. Так не нужна рефлексия по имени поля, ошибки
видны при компиляции, а с `module-info` не нужно открывать пакет модели для `javafx.base`.

`selectAndShow(contact)` (строки 31–37) выделяет строку и прокручивает таблицу к ней.
Используется после добавления, редактирования, поиска и клика по подсказке. Строка ищется
через `getItems().indexOf(contact)`, то есть через `equals`. У контактов теперь есть
`equals` по всем полям, поэтому находится и равный по значению объект, а не только тот же
самый.

## 9. TriePane: визуализация дерева

`TriePane` — это `ScrollPane` с `Canvas` внутри. Если дерево большое, его можно прокручивать
или таскать мышью (`setPannable(true)`).

### Откуда данные

`MainApp.redrawTrie()` (строки 386–389):

```java
String prefix = prefixField.getText().trim();
triePane.show(store.snapshot(prefix, depthSpinner.getValue(), MAX_VISIBLE_NODES, lastKey), prefix);
```

`snapshot` возвращает неизменяемое дерево из `TrieNodeView`. У каждого узла есть символ,
префикс, флаг конца имени (`terminal`), `subtreeSize`, флаг `visited` (лежит на пути к
`lastKey`), флаг `truncated` (есть скрытые дети) и массив детей. Фронт не видит внутренние
узлы `Trie`, а значит не может испортить структуру. Если префикса нет в дереве, возвращается
`null`.

Снимок ограничен 200 узлами и выбранной глубиной. Узлы берутся обходом в ширину, поэтому
сначала видны верхние уровни. Снимок даже на 10⁵ контактов строится за пару миллисекунд.

### Раскладка (метод `place`, строки 82–97)

Дерево рисуется слева направо. Корень слева, каждая следующая буква — следующий столбец,
и ветки читаются как слова.

```
x = MARGIN + глубина * COLUMN_WIDTH
лист:  y = MARGIN + номерСтроки * ROW_HEIGHT;  номерСтроки++
узел:  y = (y первого ребёнка + y последнего ребёнка) / 2
```

Это обход в глубину. Листья получают строки по порядку сверху вниз, а родитель встаёт
посередине между первым и последним ребёнком. Наложений не бывает, и порядок сверху вниз
алфавитный, потому что дети в `Trie` отсортированы.

Размер холста считается по числу строк и максимальной глубине (`show`, строка 64, и
`resizeCanvas`, строки 154–157). После рисования `scrollToRoot` (строки 74–80) прокручивает
холст так, чтобы корень был виден.

### Отрисовка

Рисование идёт в два прохода: сначала все рёбра (`drawEdges`, строки 99–107), потом все узлы
(`drawNodes`, строки 109–141), чтобы линии не перекрывали кружки.

| Элемент | Как рисуется |
|---|---|
| Обычный узел | белый кружок, серая обводка |
| Конец имени (в узле лежит контакт) | зелёный кружок |
| Узел на пути к `lastKey` | оранжевая толстая обводка, светло-оранжевая заливка (если это не конец имени) |
| Ребро на пути | оранжевое, толщина 2.5 (оба конца `visited`) |
| Буква в кружке | символ узла; пробел показан как `␣`; у стартового узла — `•` |
| Число над узлом | `subtreeSize` (только у развилок и листьев, чтобы не мусорить на цепочках) |
| `…` справа от узла | у узла есть дети, которые не влезли в лимит |
| Подпись стартового узла | `root (N)` или `«префикс» (N)` |

Если префикса нет в дереве (`snapshot` вернул `null`), на холсте выводится «Нет ни одного
имени с префиксом «…»».

Цвета, размеры и шрифты — константы в начале класса (строки 14–32).

### Как работает подсветка

Дерево ничего не помнит про операции. `MainApp` хранит `lastKey` — ключ последней операции
(раздел 5.1) — и передаёт его в `snapshot` четвёртым параметром. Узел получает
`visited = true`, если `lastKey` (в нижнем регистре, без пробелов по краям) начинается с
префикса этого узла. Так подсвечивается путь от корня к ключу; если ключа в дереве нет —
та часть пути, которая есть.

В первой версии подсветка хранилась в самом дереве (счётчик `stamp`), её меняла любая
операция, в том числе автодополнение. Теперь подсветку определяет только `lastKey`, и её
ничто случайно не перебивает.

## 10. Alerts

Статические методы, чтобы не повторять по 5 строк создания `Alert` в каждом обработчике:

- `error`, `info`, `warning` — простые окна;
- `warningWithDetails` — окно с текстовым полем. Используется для списка пропущенных строк
  CSV: первые 30 строк, дальше «... и ещё N» (`MainApp.showLoadErrors`, строки 250–264);
- `confirm` — да/нет перед удалением и очисткой.

## 11. Справочник для разработчика фронта

Всё ниже компилируется с текущим API. Примеры написаны как код внутри `MainApp` (пакет
`org.example.ui`), где уже есть поля `store`, `runner`, `lastKey`, `table` и методы
`refresh`, `redrawTrie`.

### 11.1. Какие методы бэкенда вызывать

| Действие в GUI | Вызов | Результат / исключения |
|---|---|---|
| Создать хранилище | `ContactStores.create()` | `TrieStore<Contact>` |
| Добавить контакт от пользователя | `store.add(contact)` | `DuplicateKeyException` (`getKey()` — имя) |
| Добавить «если можно» | `store.tryAdd(contact)` | `false`, если имя занято, без исключения |
| Изменить контакт | `store.update(oldName, newContact)` | `KeyNotFoundException` — старого нет; `DuplicateKeyException` — новое имя занято |
| Переименовать, не трогая остальное | `store.update(old.getName(), old.withName(newName))` | то же |
| Удалить | `store.removeByKey(name)` | `false`, если такого нет |
| Найти по имени | `store.findByKey(name)` | `null`, если нет; регистр и пробелы по краям не важны |
| Список для таблицы | `store.toArray()` | `Contact[]` по алфавиту |
| Автодополнение | `store.findByPrefix(prefix, limit)` | `Contact[]` длиной `min(limit, найдено)` |
| Подсчёт по префиксу | `store.countByPrefix(prefix)` | `int` |
| Размер, узлы | `store.size()`, `store.nodeCount()` | `int` |
| Очистить | `store.clear()` | — |
| Снимок для холста | `store.snapshot(prefix, maxDepth, maxNodes, highlightKey)` | `TrieNodeView` или `null`, если префикса нет |
| Загрузить CSV | `new LoadCsvTask(path, новыйStore)` | задача, результат `LoadResult` |
| Сохранить CSV | `new SaveCsvTask(path, store)` | задача, результат `Integer` (сколько записано) |
| Сгенерировать | `new GenerateContactsTask(store, count)` | задача, результат `GenerationResult`; `count <= 0` → `IllegalArgumentException` |

Пустое или `null`-имя в `add`, `findByKey`, `removeByKey`, `update` даёт
`IllegalArgumentException` (ключ не может быть пустым). Диалог не пропускает пустое имя, так
что из GUI оно туда не попадает. Префикс в `findByPrefix`, `countByPrefix` и `snapshot` может
быть пустым — это «весь справочник».

Контакты неизменяемые: чтобы что-то поменять, создайте новый объект (или `withName`) и
передайте его в `update`. `withName` сохраняет тип:

```java
CorporateContact renamed = corporate.withName("Ирина Белова");   // должность и номер те же
```

### 11.2. Как ловить ошибки

Оба исключения хранилища — `RuntimeException`, компилятор не заставит их ловить. Ловите
явно там, где пользователь может их вызвать:

```java
try {
    store.update(selected.getName(), updated);
} catch (DuplicateKeyException e) {
    Alerts.error("Контакт с именем «" + e.getKey() + "» уже есть.");
    return;
} catch (KeyNotFoundException e) {
    Alerts.error("Контакт «" + e.getKey() + "» уже удалён.");
    refresh("Таблица обновлена");
    return;
}
```

Ошибки внутри фоновых задач (например, `IOException` при чтении файла) ловить не нужно:
задача переходит в состояние FAILED, и `BackgroundRunner` сам показывает `Alerts.error`.

Ошибки разбора CSV не роняют загрузку: битые строки пропускаются и лежат в
`LoadResult.getErrors()`. У каждой есть `getLineNumber()`, `getErrorCode()` и `getMessage()`:

```java
for (CsvParseException e : result.getErrors()) {
    System.out.println("Строка " + e.getLineNumber() + ": " + e.getMessage() + " [" + e.getErrorCode() + "]");
}
```

### 11.3. Как запускать долгие операции

Правило: всё, что может занять больше 100 мс, — в задаче через `runner.run(...)`. Внутри
`call()` нельзя трогать элементы окна; результат обрабатывается в колбэках, они уже в
FX-потоке.

**Загрузка** (обычный `Task`, отмена через `cancel()`):

```java
TrieStore<Contact> loaded = ContactStores.create();
runner.run(new LoadCsvTask(file.toPath(), loaded), result -> {
    store = loaded;
    lastKey = null;
    refresh("Загружено " + result.getLoaded() + " из " + file.getName());
}, () -> statusLabel.setText("Загрузка отменена, данные не изменились"));
```

**Генерация** (`StoppableTask`, «Отмена» = мягкая остановка, итог всегда в `onSuccess`):

```java
runner.run(new GenerateContactsTask(store, count),
        result -> refresh(result.stopped()
                ? "Генерация остановлена, добавлено " + result.added() + " из " + result.requested()
                : "Сгенерировано " + result.added()),
        () -> refresh("Генерация отменена"));
```

**Своя новая операция.** Если операция пишет в рабочее хранилище и после отмены нужно
знать точный итог — наследуйтесь от `StoppableTask` и проверяйте `shouldStop()` в цикле:

```java
class RemoveByPrefixTask extends StoppableTask<Integer> {
    private final TrieStore<Contact> store;
    private final String prefix;

    RemoveByPrefixTask(TrieStore<Contact> store, String prefix) {
        this.store = store;
        this.prefix = prefix;
    }

    @Override
    protected Integer call() {
        Contact[] victims = store.findByPrefix(prefix, store.countByPrefix(prefix));
        int removed = 0;
        for (Contact c : victims) {
            if (shouldStop()) {
                break;
            }
            if (store.removeByKey(c.getName())) {
                removed++;
            }
            updateProgress(removed, victims.length);
        }
        return removed;
    }
}
```

```java
runner.run(new RemoveByPrefixTask(store, "ив"),
        removed -> refresh("Удалено " + removed),
        () -> refresh("Удаление отменено"));
```

`runner.cancel()` сам поймёт, что это `StoppableTask`, и вызовет `requestStop()`. Если же
операция пишет во временное хранилище (как загрузка), достаточно обычного `Task` и проверки
`isCancelled()`.

Чего не делать:

- не создавать `new Thread(task)` самим — используйте `runner.run`, тогда работают прогресс,
  блокировка кнопок и `shutdown()` при закрытии окна;
- не вызывать `refresh` или менять `rows` из `call()`;
- не запускать вторую задачу, пока идёт первая: `runner.run` её просто проигнорирует.

### 11.4. Как получить подсветку

1. После операции запишите её ключ в `lastKey`.
2. Вызовите `refresh(...)` (или только `redrawTrie()`, если таблица не менялась).

```java
lastKey = name;
Contact found = store.findByKey(name);
redrawTrie();
```

`lastKey = null` — без подсветки. Сам снимок можно взять и вне `MainApp`, например для
отладки в консоли:

```java
TrieNodeView view = store.snapshot("ив", 25, 200, "Иван Петров");
System.out.print(TriePrinter.print(view));      // подсвеченные узлы помечены *
```

## 13. Вопросы по фронту на защите

- **Почему таблица использует ObservableList, хотя списки запрещены?** Запрещены как основное
  хранилище. `rows` — копия для показа: `TableView` принимает только `ObservableList`. Все
  операции идут в `TrieStore`, а таблица после них перезаполняется из `store.toArray()`.
- **В каком потоке выполняется `setOnSucceeded`?** В FX-потоке. Поэтому в нём можно обновлять
  таблицу. В `call()` трогать GUI нельзя.
- **Что будет, если обновить таблицу из `call()`?** `IllegalStateException: Not on FX
  application thread` или непредсказуемые глюки.
- **Зачем `ExecutorService`, а не `new Thread`?** Один поток на всё приложение, задачи идут
  строго по очереди, а при закрытии окна его можно корректно остановить (`shutdown()` из
  `MainApp.stop()`).
- **Как работает отмена?** Для загрузки и сохранения — `task.cancel()`: задача сразу
  отменена, загрузчик на следующей строке видит `isCancelled()` и выходит. Для генерации —
  `requestStop()`: ставится `volatile`-флаг, генератор выходит из цикла, задача завершается
  нормально и возвращает точное число добавленных.
- **Почему для генерации не подходит `cancel()`?** После `cancel()` `onCancelled` вызывается
  сразу, а фоновый поток ещё может вставлять. Число, посчитанное в этот момент, неточное.
- **Почему `volatile` у флага остановки?** Флаг ставит FX-поток, а читает рабочий. Без
  `volatile` рабочий поток может долго не увидеть изменение.
- **Как GUI отличает «имя занято» от «контакт удалён»?** Хранилище бросает разные исключения:
  `DuplicateKeyException` и `KeyNotFoundException`. У обоих есть `getKey()` для сообщения.
- **Почему кнопка «Изменить» управляется binding'ом?** Состояние кнопки само пересчитывается
  при смене выделения или флага `busy`, не нужно помнить об этом в каждом обработчике.
- **Почему `TriePane` не рисует всё дерево?** На 10⁵ контактов около 800 тыс. узлов. Холст
  такого размера не создать, а строить его на FX-потоке слишком долго. Поэтому рисуется
  поддерево префикса с лимитом 200 узлов.
- **Откуда холст знает, что подсвечивать?** `MainApp` хранит `lastKey` — ключ последней
  операции — и передаёт его в `snapshot`. Узел подсвечен, если `lastKey` начинается с его
  префикса.
- **Важен ли порядок вызовов в `refresh()`?** Для подсветки — нет. Чтения из хранилища не
  меняют дерево, а подсветку определяет только `lastKey`. (В первой версии автодополнение
  перебивало подсветку, и порядок был важен.)
- **Можно ли во время генерации пользоваться поиском?** Да. Поиск — чтение под блокировкой
  чтения, а генератор берёт блокировку записи только на время одной вставки.
