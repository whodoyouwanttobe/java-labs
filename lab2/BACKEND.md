# Гайд по бэкенду, лабораторная 2

Бэкенд в этом проекте — всё, кроме пакета `org.example.ui`: модель, собственная структура
данных, загрузка и сохранение CSV, генератор, фоновые задачи, демонстрации и тесты.
GUI вызывает бэкенд, а бэкенд про GUI ничего не знает.

Номера строк в этом файле указаны для текущей версии кода (после исправлений). Если будете
менять код, номера сдвинутся.

## 2. Архитектура: слои и зависимости

```
          ui (фронт)
             │
             ▼
           tasks  ─────────────┐        javafx.concurrent.Task — единственное место бэка,
             │                 │        где есть JavaFX
     ┌───────┼──────────┐      │
     ▼       ▼          ▼      │
    csv   generator   store ◄──┘
     │       │          │
     └───────┴────┬─────┘
                  ▼
                model
```

Правила:

- **Зависимости идут только вниз.** `store` не знает про CSV и GUI, `model` не знает ни о ком.
  Поэтому `Trie` можно тестировать отдельно, а лабу 5 (Spring) подключить к тому же `TrieStore`
  без изменений.
- **`csv` и `generator` работают через интерфейс `EntityStore<String, Contact>`,** а не через
  конкретный `TrieStore`. Если поменять структуру, загрузчик не изменится.
- **JavaFX в бэке есть только в `tasks`.** Сами `CsvLoader` и `ContactGenerator` сообщают
  прогресс через свой интерфейс `ProgressListener` и проверяют отмену через `BooleanSupplier`.
  Это обычная Java, поэтому их можно вызывать из консоли и тестов, а потом из Spring.

## 3. Модель

```
Contact (имя, телефон, e-mail, организация)
 ├── EmergencyContact                    — read-only, только из файла
 └── CorporateContact implements Editable — + должность, внутренний номер
```

- `Editable` — интерфейс с методом `validate()`, который возвращает список ошибок (пустой = ок).
  Выбран вариант «с методом», а не маркер: проверка полей живёт в самой сущности, и GUI вызывает
  её, не зная конкретный тип.

### 3.1. Контакты неизменяемые

Все поля `final`, сеттеров нет (`Contact.java`, строки 6–9; `CorporateContact.java`,
строки 8–9). Чтобы «поменять» контакт, создаётся новый объект.

Для переименования есть `withName` — он возвращает копию **того же типа** с новым именем:

```java
public Contact withName(String newName) {                       // Contact.java, строки 34–36
    return new Contact(newName, phone, email, organization);
}

@Override
public CorporateContact withName(String newName) {              // CorporateContact.java, строки 26–29
    return new CorporateContact(newName, phone, email, organization, position, internalNumber);
}
```

В `EmergencyContact` то же самое (строки 8–11). Тип результата в наследниках уже, чем в
`Contact` (ковариантный возвращаемый тип), поэтому `corporate.withName(...)` сразу даёт
`CorporateContact` без приведения.

**Почему неизменяемые:**

- **Ключ в дереве не может «уехать».** Контакт лежит в `Trie` под своим именем. Если бы у
  объекта был `setName`, кто-нибудь (например, GUI) мог бы поменять имя прямо у объекта в
  дереве. Тогда контакт лежал бы под старым ключом и перестал бы находиться. Теперь сменить
  имя можно только через `store.update(староеИмя, новыйОбъект)`.
- **Безопасно между потоками.** Объект с `final`-полями после конструктора виден другим потокам
  полностью, его можно читать без блокировок.
- **Генератору это тоже удобно:** при совпадении имени он делает `contact.withName(имя + " 2")`
  и не теряет тип и остальные поля (раздел 9).

### 3.2. `equals` и `hashCode`

`Contact.java`, строки 42–60; `CorporateContact.java`, строки 51–61.

- Два контакта равны, если у них одинаковый класс (`getClass()`) и одинаковые все поля.
  `Contact` и `CorporateContact` с одинаковыми базовыми полями не равны.
- `hashCode` согласован с `equals` (одинаковые объекты дают одинаковый хеш).
- Где это нужно: тест «сохранить → загрузить» сравнивает контакт целиком
  (`assertEquals(tricky, loaded.findByKey(...))`), а таблица во фронте ищет строку через
  `indexOf`, то есть через `equals`.
- Для неизменяемых объектов сравнение по значению — естественное поведение: объект и есть
  его данные.

## 4. Контракт хранилища

```java
public interface EntityStore<K, T> {        // EntityStore.java, строки 3–20
    void add(T entity);                     // DuplicateKeyException, если ключ занят
    boolean tryAdd(T entity);               // false, если ключ занят
    T findByKey(K key);                     // null, если нет
    boolean removeByKey(K key);
    void update(K oldKey, T entity);        // KeyNotFoundException или DuplicateKeyException
    int size();
    void clear();
    T[] toArray();                          // все записи в порядке ключей
}

public interface PrefixStore<T> extends EntityStore<String, T> {
    T[] findByPrefix(String prefix, int limit);   // автодополнение
    int countByPrefix(String prefix);             // подсчёт в поддереве
}
```

Оба исключения — `RuntimeException`, у обоих есть `getKey()` (какой ключ виноват):

```java
public class DuplicateKeyException extends RuntimeException {   // аналогично KeyNotFoundException
    public DuplicateKeyException(String key) { ... }
    public String getKey() { ... }
}
```

**Почему так:**

- **Интерфейс, а не сразу класс.** Это рекомендация задания: «начните с контракта». GUI и CSV
  зависят от контракта, а реализацию можно подменить. В лабе 5 это будет Spring-бин.
- **Два интерфейса.** `EntityStore` — общий CRUD для любой структуры. `PrefixStore` добавляет
  то, что имеет смысл только для строковых ключей и префиксного дерева.
- **Два способа добавить: `add` и `tryAdd`.**
  - `add` — для действий пользователя. Дубликат здесь — ошибка, которую надо показать, поэтому
    бросается `DuplicateKeyException` с ключом.
  - `tryAdd` — для массовых операций, где дубликат — обычная ситуация: повтор в файле,
    генератор выдал то же имя. Исключение на каждый повтор было бы дорого и неудобно, поэтому
    просто `false`. Загрузчик и генератор используют `tryAdd`.
- **`update` бросает разные исключения, а не возвращает `boolean`.** Раньше `update` возвращал
  `false`, и было непонятно почему: то ли старого контакта уже нет, то ли новое имя занято.
  Теперь причины разные:
  - `KeyNotFoundException` — старого ключа нет (контакт удалили);
  - `DuplicateKeyException` — новое имя занято другим контактом.

  GUI ловит их по отдельности и показывает правильное сообщение: «уже есть» или «уже удалён».
  В лабе 5 это превратится в разные HTTP-коды: 409 Conflict и 404 Not Found.
- **`update(oldKey, entity)`.** После редактирования имя, то есть ключ, могло поменяться.
  Хранилище атомарно проверяет, что старый есть, а новое имя свободно, удаляет запись по
  старому ключу и кладёт по новому.
- **Результаты — массивы `T[]`, а не `List`.** Списки запрещены как хранилище. Массив — простой
  результат фиксированной длины, и его размер известен заранее (`min(limit, subtreeSize)`).

## 5. Trie — как устроено дерево

### 5.1. Узел

```java
private static final class Node<V> {        // Trie.java, строки 9–85
    final char symbol;                      // буква, по которой пришли в узел
    final Node<V> parent;                   // нужен для подъёма при удалении

    char[] symbols = new char[0];           // буквы детей, ОТСОРТИРОВАНЫ
    Node<V>[] children = newNodes(0);       // дети в том же порядке
    int childCount;                         // сколько ячеек реально занято

    V value;                                // контакт, если здесь кончается имя; иначе null
    int subtreeSize;                        // сколько значений в поддереве (включая этот узел)
}
```

Поля дерева (строки 87–88):

- `root` — корень с символом `'\0'`;
- `nodeCount` — число узлов.

Размер дерева не хранится отдельно: это `root.subtreeSize`.

Служебных полей для подсветки в узле нет: дерево хранит только данные. Подсветка считается
при построении снимка (раздел 5.10).

### 5.2. Пример

Ключи `иван`, `иванов`, `ирина`, `анна` (после нормализации):

```
root(4)
├── а(1) ─ н ─ н ─ а$
└── и(3)
    ├── в(2) ─ а ─ н$(2) ─ о ─ в$
    └── р(1) ─ и ─ н ─ а$
```

- `$` — в узле лежит значение;
- число — `subtreeSize`;
- у корня два ребёнка `['а','и']`, у `и` — `['в','р']`, массивы отсортированы.

`countWithPrefix("и")` = 3: спускаемся в `и` и читаем его `subtreeSize`.

### 5.3. Дети: сортированный массив и бинарный поиск

Варианты хранения детей и почему выбран последний:

| Вариант | Минус |
|---|---|
| `Node[33]` по алфавиту | в именах кириллица, латиница, цифры, пробел, дефис → нужен массив на тысячи символов в каждом узле |
| `HashMap<Character, Node>` | запрещено (java.util как основа структуры) |
| связный список детей | поиск ребёнка O(σ), порядок не алфавитный |
| **сортированные `char[]` + `Node<V>[]`** | **поиск O(log σ), обход сразу в алфавитном порядке, память по факту** |

```java
int indexOf(char c) {                 // Trie.java, строки 25–39
    int lo = 0;
    int hi = childCount - 1;
    while (lo <= hi) {
        int mid = (lo + hi) >>> 1;
        if (symbols[mid] < c) {
            lo = mid + 1;
        } else if (symbols[mid] > c) {
            hi = mid - 1;
        } else {
            return mid;
        }
    }
    return -(lo + 1);                 // не нашли: закодированная позиция вставки
}
```

`-(lo + 1)` — тот же приём, что в `Arrays.binarySearch`. Одно число говорит и «не найден»,
и «куда вставлять».

`addChild(c)` (строки 46–68):

1. если ребёнок уже есть — вернуть его;
2. если массив полон — создать новый вдвое больше и скопировать (`System.arraycopy`);
3. сдвинуть хвост на одну позицию вправо и вставить нового ребёнка на своё место.

`removeChild(c)` (строки 70–79) сдвигает хвост влево и обнуляет освободившуюся ячейку.

### 5.4. Нормализация ключа

```java
public static String normalize(String key) {     // Trie.java, строки 90–99
    if (key == null) {
        throw new IllegalArgumentException("Ключ не может быть null");
    }
    String result = key.trim().toLowerCase(Locale.ROOT);
    if (result.isEmpty()) {
        throw new IllegalArgumentException("Ключ не может быть пустым");
    }
    return result;
}
```

- «Иван», «иван» и « ИВАН » — один ключ. Для справочника это ожидаемо, и автодополнение
  не зависит от регистра.
- `Locale.ROOT` нужен, чтобы результат не зависел от языка системы. Классический пример —
  турецкая «I».
- Пустой ключ запрещён: иначе значение легло бы прямо в корень.
- Для префиксов есть `normalizePrefix` (строки 101–103): там `null` и пустая строка разрешены
  и означают «весь корень».

### 5.5. Вставка `insert(key, value, replace)`

`Trie.java`, строки 202–225.

1. Нормализовать ключ.
2. Для каждого символа вызвать `addChild` (найти или создать ребёнка). Если у родителя стало
   больше детей, значит узел создан: `nodeCount++`.
3. В конечном узле:
   - значения не было → положить значение и подняться по `parent` до корня, делая
     `subtreeSize++`;
   - было и `replace == true` → заменить значение (размер не меняется);
   - было и `replace == false` → ничего не делать.

`put` — вставка с заменой, `putIfAbsent` — без замены (используется хранилищем)
(строки 131–137). `putIfAbsent` возвращает `true`, если значение добавлено.

### 5.6. Поиск `get(key)`

`find(k)` (строки 227–233) — спуск по символам. Если ребёнка нет, возвращается `null`.

`get` (строки 122–125) возвращает `node.value`. Если путь есть, но значение не лежит
(например, `ива` при наличии `иван`), результат тоже `null`.

**Поиск ничего не записывает в дерево.** В первой версии он помечал пройденные узлы для
подсветки, теперь — нет. Это важно для многопоточности (раздел 10).

### 5.7. Удаление `remove(key)`

`Trie.java`, строки 139–157.

1. Найти узел (`find`). Если его нет или значения нет — вернуть `null`.
2. Обнулить `value` и подняться до корня, делая `subtreeSize--`.
3. **Срезать ветку:** пока текущий узел не корень, без значения и без детей, удалить его
   из родителя (`nodeCount--`) и перейти к родителю.

```
удаляем "анна":  а─н─н─а$  →  все 4 узла пустые и без детей → срезаны
удаляем "иван":  н$ имеет ребёнка "о" (иванов) → узел остаётся, только value = null
```

Без срезки дерево копило бы мёртвые ветки, и `nodeCount` рос бы бесконечно.

### 5.8. Подсчёт в поддереве `countWithPrefix(prefix)`

`Trie.java`, строки 159–162. Спуск по префиксу и возврат `node.subtreeSize`. Поддерево не
обходится. Это главное преимущество хранения счётчика в узле: цена O(P·log σ) не зависит от
того, сколько контактов под префиксом.

Пустой префикс — это корень, то есть все контакты.

### 5.9. Автодополнение `findWithPrefix(prefix, limit, arrayFactory)`

`Trie.java`, строки 164–175, обход `collect` — строки 235–246.

1. Спуститься к узлу префикса.
2. Создать массив ровно на `min(limit, node.subtreeSize)` элементов.
3. Обход в глубину `collect`: сначала значение узла, потом дети по порядку. Как только массив
   заполнен, обход останавливается.

Дети отсортированы, поэтому результат в алфавитном порядке, и ничего досортировывать не нужно.
`values()` (строки 177–181, через него работает `toArray()`) — тот же обход от корня.

### 5.10. Подсветка: ключ передаётся в снимок

Задача — показать на картинке узлы, через которые прошла **последняя** операция.

Как это сделано теперь: дерево ничего не помнит про операции. Тот, кто рисует, сам знает,
какой ключ был в последней операции, и передаёт его в снимок:

```java
store.snapshot(prefix, maxDepth, maxNodes, highlightKey)
```

Узел подсвечивается (`visited = true`), если `highlightKey` начинается с префикса этого узла
(`Trie.java`, строки 328–330):

```java
private boolean isOnPath(String prefix) {
    return highlight != null && highlight.startsWith(prefix);
}
```

`highlightKey` нормализуется так же, как префикс (строка 197), поэтому регистр не важен.

Пример: `highlightKey = "ивар"`, в дереве есть `иван`. Узлы `и`, `ив`, `ива` подсвечены
(«ивар» с них начинается), а `иван` — нет. Получается та часть пути, которую прошёл бы поиск
до обрыва, — ровно как раньше.

Если `highlightKey == null`, ничего не подсвечено.

**Как было в первой версии и почему переделано.** Раньше у дерева был счётчик операций
`stamp`, а каждая операция (в том числе поиск и автодополнение) записывала его номер в
пройденные узлы. Минусы:

- чтение меняло дерево, поэтому даже поиск должен был брать эксклюзивную блокировку;
- подсветку «перебивала» любая операция, например автодополнение, и во фронте приходилось
  следить за порядком вызовов.

Теперь `get`, `findWithPrefix` и `countWithPrefix` не имеют побочных эффектов. Это проверяет
тест `readsDoNotChangeSnapshot`.

### 5.11. Снимок для визуализации `snapshot(prefix, maxDepth, maxNodes, highlightKey)`

GUI не должен видеть внутренние `Node`, иначе он мог бы испортить структуру. Поэтому отдаётся
неизменяемая копия:

```java
public record TrieNodeView(char symbol, String prefix, boolean terminal, int subtreeSize,
                           boolean visited, boolean truncated, TrieNodeView[] children) { }
```

Публичный метод — `Trie.java`, строки 191–200. Он находит узел префикса (если его нет —
возвращает `null`) и отдаёт работу внутреннему классу `SnapshotBuilder` (строки 259–331).
Есть и короткая версия `snapshot(maxDepth)` (строки 187–189): всё дерево, без подсветки.

Ограничения:

- На 10⁵ контактов около 800 тыс. узлов, всё это не нарисовать. Поэтому снимок строится
  от узла префикса и ограничен глубиной и числом узлов.
- Обход в ширину выбран потому, что обход в глубину израсходовал бы лимит на одну длинную
  ветку, а в ширину сначала видны верхние уровни.

Как работает `SnapshotBuilder`:

1. **Обход в ширину в параллельные массивы** (`collectBreadthFirst`, строки 305–326). Все
   массивы длиной `maxNodes`, индекс `i` описывает один отобранный узел:

   | Массив | Что лежит в ячейке `i` |
   |---|---|
   | `nodes[i]` | сам узел |
   | `prefixes[i]` | его префикс (префикс родителя + буква) |
   | `parents[i]` | индекс родителя (у стартового узла `-1`) |
   | `depths[i]` | глубина от стартового узла |
   | `firstChild[i]` | индекс первого отобранного ребёнка |
   | `includedChildren[i]` | сколько детей попало в снимок |

   Сам массив `nodes` и есть очередь: `head` идёт по нему, новые узлы дописываются в конец
   (`count`). Никакого `java.util.Queue` нет. Дети одного узла попадают в массив подряд,
   поэтому достаточно помнить, где начинается первый. Обход останавливается, когда массив
   заполнен, а узлы глубже `maxDepth` не раскрываются.
2. **Сборка `TrieNodeView` в обратном порядке** (`build`, строки 286–303). При обходе в
   ширину ребёнок всегда стоит в массиве **после** родителя. Если идти с конца, то к моменту
   создания узла все его дети уже созданы, и их можно сразу положить в его массив `children`.
   Так снимок собирается без рекурсии, одним циклом.
3. `truncated = true`, если показаны не все дети узла (`includedChildren[i] < childCount`).

Снимок на 10⁵ контактов строится за пару миллисекунд, потому что обходится не больше
`maxNodes` узлов.

## 6. TrieStore — обёртка-хранилище

```java
public class TrieStore<T> implements PrefixStore<T> {        // TrieStore.java, строки 9–19
    private final Trie<T> trie = new Trie<>();
    private final Function<? super T, String> keyOf;          // как достать ключ из сущности
    private final IntFunction<T[]> arrayFactory;              // как создать массив T[n]
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
    ...
}

TrieStore<Contact> store = new TrieStore<>(Contact::getName, Contact[]::new);
// то же самое: ContactStores.create()
```

- **Зачем `keyOf`.** `Trie` хранит пары «строка → значение» и про контакты не знает. Хранилище
  принимает целую сущность и само достаёт ключ. Ту же структуру можно использовать для любого
  типа, например в `RaceDemo` с `Integer`.
- **Зачем `arrayFactory`.** В Java нельзя написать `new T[n]`: из-за стирания типов в рантайме
  `T` неизвестен. `Contact[]::new` — это функция `n → new Contact[n]`, так же устроен
  `Collection.toArray(IntFunction)`.
- **`add` сделан через `tryAdd`** (строки 21–32): если `tryAdd` вернул `false`, бросается
  `DuplicateKeyException`.
- **Чтение под блокировкой чтения, запись — под блокировкой записи.** Для этого два
  вспомогательных метода (строки 104–122):

  ```java
  private <R> R read(Supplier<R> action) {
      Lock r = lock.readLock();
      r.lock();
      try {
          return action.get();
      } finally {
          r.unlock();
      }
  }
  ```

  `write` такой же, только с `lock.writeLock()`. Каждый публичный метод — одна строка:
  `findByKey` → `read(() -> trie.get(key))`, `removeByKey` → `write(() -> trie.remove(key) != null)`.
  `unlock` в `finally`, поэтому блокировка снимается даже при исключении. Подробнее — раздел 10.
- **`update` атомарен** (строки 44–62). Проверка «старый есть, новый свободен», удаление и
  вставка идут под одной блокировкой записи. Между ними другой поток не вклинится:

  ```java
  if (!trie.containsKey(oldNorm)) {
      throw new KeyNotFoundException(oldKey);
  }
  if (!oldNorm.equals(newNorm) && trie.containsKey(newNorm)) {
      throw new DuplicateKeyException(keyOf.apply(entity));
  }
  trie.remove(oldNorm);
  trie.put(newNorm, entity);
  ```

  Если имя не поменялось (`oldNorm.equals(newNorm)`), это не дубликат: контакт просто
  заменяется новой версией с другим телефоном или должностью.

## 7. Дженерики (уровень «максимум»)

| Класс | Параметр | Смысл |
|---|---|---|
| `Trie<V>` | `V` — значение | ключ всегда `String` (это префиксное дерево) |
| `Node<V>` | `V` | узел хранит `V value`, дети — `Node<V>[]` |
| `EntityStore<K, T>` | `K` — ключ, `T` — сущность | общий контракт любой структуры |
| `PrefixStore<T>` | `T` | `K` зафиксирован как `String` |
| `TrieStore<T>` | `T` | + `Function<? super T, String>` |

`? super T` в `keyOf` позволяет передать функцию для родительского типа. Например,
`Contact::getName` подходит и для `TrieStore<CorporateContact>`.

**Узел обобщённый.** В первой версии значение лежало в поле `Object value`, и при каждом
чтении его приходилось приводить к `V`. Теперь `Node<V>` хранит `V value`, и `get`,
`collect`, `remove` возвращают `V` без приведений — ошибку типа поймает компилятор.

Одно место без проверки всё же осталось: в Java нельзя написать `new Node<V>[n]` (массив
обобщённого типа). Поэтому массив создаётся как `new Node[n]` и приводится в одном методе
`newNodes` (строки 81–84) с `@SuppressWarnings("unchecked")`; то же самое в конструкторе
`SnapshotBuilder` (строки 270–274). Это безопасно: в такой массив кладутся только `Node<V>`.

## 8. CSV

Формат (как в лабе 1, разделитель `;`, первая строка — заголовок):

```
Тип;Имя;Телефон;Email;Организация;Должность;Внутренний номер
Corporate;Иван Иванов;+79991234567;ivan@example.com;ООО Вектор;Менеджер;101
Emergency;Служба спасения;112;112@mchs.gov;МЧС
Contact;Петр Петров;+79990001122;petr@example.com;ИП Петров
```

### 8.1. Кавычки: `CsvFormat`

В первой версии строка резалась простым `split(";")`. Если в названии организации была `;`
(«ООО Рога; Копыта»), поля съезжали, а сохранённый файл нельзя было загрузить обратно.

Теперь разбор и запись — в `CsvFormat.java`, по правилам, как в RFC 4180, только с
разделителем `;`:

- поле можно взять в двойные кавычки, тогда `;` внутри — обычный символ;
- кавычка внутри такого поля пишется двумя кавычками: `""` → `"`;
- после закрывающей кавычки должен идти `;` или конец строки.

```
Contact;"ООО Рога; Копыта";x          → ["Contact", "ООО Рога; Копыта", "x"]
"ООО ""Альфа"""                       → ["ООО "Альфа""]
a;"bc;d                               → BAD_QUOTES (кавычка не закрыта)
"ab"c;d                               → BAD_QUOTES (текст после закрывающей кавычки)
```

`split(line, lineNumber)` (строки 14–49) идёт по символам с флагом `quoted` («мы внутри
кавычек»):

- внутри кавычек всё добавляется в поле, кроме кавычки; `""` даёт одну кавычку; одиночная
  кавычка закрывает поле;
- снаружи `;` завершает поле, а кавычка в начале поля открывает кавычки.

`escape(value)` (строки 51–61) — обратная операция для записи: `null` → пустая строка,
переводы строк заменяются пробелом, а если в значении есть `;` или `"` — значение берётся в
кавычки с удвоением внутренних кавычек. Обычный текст пишется как есть, так что файл
остаётся читаемым.

`CsvFormat` — класс пакета `csv` (не `public`): снаружи он не нужен, им пользуются только
`CsvLoader` и `CsvSaver`.

### 8.2. Загрузка `CsvLoader.load(file, target, progress, cancelled)`

`CsvLoader.java`, строки 30–66.

1. Узнать размер файла в байтах: `Files.size(file)` (строка 32). Это не чтение файла, а
   запрос к файловой системе, он мгновенный.
2. Открыть файл через `CountingInputStream` и читать построчно `BufferedReader` в UTF-8
   (строки 36–37).
3. На каждой строке проверять отмену, каждые 500 строк сообщать прогресс
   `progress.onProgress(counter.getCount(), totalBytes)` — сколько байт прочитано из скольких.
4. Каждую строку разобрать через `parseLine` и добавить в хранилище через `tryAdd`:
   - битая строка → `CsvParseException` с номером строки и кодом, строка пропускается,
     ошибка копится в `LoadResult`;
   - `tryAdd` вернул `false` → ошибка `DUPLICATE_NAME`.
5. В конце сообщить `onProgress(totalBytes, totalBytes)` (100%) и вернуть
   `LoadResult(loaded, errors, cancelled)`.

**Прогресс в байтах вместо строк.** В первой версии файл читался **дважды**: сначала
`Files.lines(...).count()`, чтобы узнать число строк, потом второй раз для разбора. На
большом файле это почти удваивало время. Теперь файл читается один раз, а общий объём
берётся из `Files.size`.

`CountingInputStream` (43 строки) — обёртка над `InputStream` (`FilterInputStream`), которая
в `read` и `skip` прибавляет к счётчику, сколько байт прошло. Она стоит **под**
`BufferedReader`, поэтому считает байты, которые уже забраны из файла (вместе с буфером
чтения). Счётчик слегка «забегает вперёд» относительно разобранных строк, но для полосы
прогресса это не важно. Тест `progressIsReportedInBytesUpToFileSize` проверяет, что прогресс
не убывает и заканчивается ровно на `Files.size`.

`parseLine` (строки 68–103) — сначала `CsvFormat.split`, затем проверки полей. Он публичный,
чтобы его можно было тестировать на одной строке (пригодится в лабе 3).

| Код | Когда |
|---|---|
| `WRONG_FIELD_COUNT` | меньше 5 полей, у Corporate меньше 7 |
| `EMPTY_REQUIRED_FIELD` | пустое имя |
| `BAD_NUMBER` | внутренний номер не из цифр |
| `UNKNOWN_TYPE` | тип не `Contact` / `Emergency` / `Corporate` |
| `DUPLICATE_NAME` | такое имя уже загружено |
| `BAD_QUOTES` | незакрытая кавычка или текст сразу после закрывающей кавычки |

### 8.3. Сохранение `CsvSaver.save(file, store)`

`CsvSaver.java`, строки 17–28. Берёт `store.toArray()` (контакты по алфавиту), пишет
заголовок и строки и возвращает их число. Каждое поле проходит через `CsvFormat.escape`
(строки 44–46), поэтому `null` пишется пустой строкой, а поля с `;` и `"` — в кавычках.
Тест `roundTripWithSeparatorAndQuotesInFields` сохраняет контакт с `;` и кавычками во всех
полях, загружает обратно и сравнивает через `equals`.

## 9. Генератор

`ContactGenerator`:

- Набор имён: 30 фамилий × 30 имён × 17 отчеств ≈ 15 000 сочетаний.
- Телефон: `+79` и 9 случайных цифр.
- E-mail: `user<номер>@<домен>`.
- 40% контактов корпоративные (`CORPORATE_SHARE`).
- Можно задать seed (`new ContactGenerator(42)`): тогда данные воспроизводимы, это нужно для

`generateInto(store, count, progress, cancelled)` (строки 71–91) добавляет **ровно** `count`
контактов. Если имя занято (на 10⁵ это неизбежно), к нему дописывается номер: «Иванов Иван
Иванович 2», «… 3», и так далее:

```java
Contact contact = next();
String baseName = contact.getName();
int suffix = 2;
while (!store.tryAdd(contact)) {
    contact = contact.withName(baseName + " " + suffix++);
}
```

- `tryAdd`, а не `add`: повтор имени здесь ожидаем, исключение на каждый повтор не нужно.
- `withName` возвращает копию того же типа, поэтому корпоративный контакт остаётся
  корпоративным со своей должностью и номером. Раньше для этого был сеттер имени.

Метод возвращает, сколько реально добавлено: при отмене меньше `count`.

Read-only контакты генератор не создаёт: по заданию они появляются только из файла.

## 10. Многопоточность

### Где возникает гонка

Если два потока одновременно пишут в голый `Trie`:

1. **`addChild`:** оба видят `childCount = 3`, оба пишут в ячейку 3 и делают `childCount++`.
   Один ребёнок затёрт, вместе с ним пропадает целая ветка.
2. **Расширение массива:** поток A создал новый массив и копирует в него, а поток B в это время
   пишет в старый. Запись теряется. Возможен `ArrayIndexOutOfBoundsException`.
3. **`subtreeSize++`:** это чтение, увеличение и запись, а не атомарная операция. Обновления
   теряются, и `size()` врёт.

Чтение параллельно с записью тоже опасно: читатель идёт по массиву детей, который запись в
этот момент сдвигает или заменяет новым.

### Демонстрация `RaceDemo`

- 8 потоков по 20 000 вставок вперемешку, ожидается 160 000.
- Голый `Trie`: `size()` меньше 160 000, часть вставок падает с исключением, часть ключей
  потом не находится.
- `TrieStore` (в выводе — «С ReadWriteLock (TrieStore)»): ровно 160 000, падений 0.

Цифры для голого `Trie` каждый раз немного разные — это и есть признак гонки.

### Защита: `ReentrantReadWriteLock`

В `TrieStore` одна блокировка с двумя «замками»:

- **блокировка чтения** (`readLock`) — её могут держать **сколько угодно потоков сразу**;
- **блокировка записи** (`writeLock`) — только **один** поток, и пока она взята, читателей нет.

| Методы | Блокировка |
|---|---|
| `findByKey`, `findByPrefix`, `countByPrefix`, `toArray`, `size`, `nodeCount`, `snapshot` | чтения |
| `add`/`tryAdd`, `removeByKey`, `update`, `clear` | записи |

Итого: читатели не мешают друг другу, писатель работает один и видит дерево целиком, читатели
никогда не видят дерево «посередине» вставки.

**Почему раньше было `synchronized` на всём, а теперь можно `ReadWriteLock`.** В первой версии
поиск и автодополнение записывали `stamp` и `visitStamp` в узлы для подсветки. То есть
«чтение» на самом деле было записью. Если бы два поиска шли параллельно под блокировкой
чтения, они бы одновременно меняли `stamp` — та же гонка. Поэтому приходилось пускать по одному
потоку на любые операции. Теперь подсветка передаётся в снимок (раздел 5.10), чтение
ничего не пишет, и несколько читателей действительно могут работать вместе.

Это проверяет тест `readersRunWhileWriterInserts`: один поток вставляет 20 000 ключей, три
потока в это время делают `countByPrefix` и `findByPrefix`. Ни одного исключения у читателей,
в конце ровно 20 000.

`Trie` специально оставлен без синхронизации. Это «чистая» структура, синхронизация —
ответственность обёртки. Поэтому `RaceDemo` может показать гонку на том же самом классе.

### Кто реально работает параллельно

- Фоновые задачи (генерация, загрузка) пишут в хранилище из своего потока.
- Одновременно FX-поток читает его: клик по строке таблицы, ввод префикса, перерисовка дерева.

## 11. Фоновые задачи (`tasks`)

### 11.1. Обычная задача: `LoadCsvTask`, `SaveCsvTask`

```java
public class LoadCsvTask extends Task<LoadResult> {
    @Override
    protected LoadResult call() throws Exception {           // LoadCsvTask.java, строки 21–27
        updateMessage("Загрузка " + file.getFileName());
        LoadResult result = new CsvLoader().load(file, target, this::updateProgress, this::isCancelled);
        updateMessage("Загружено: " + result.getLoaded() + ", пропущено строк: " + result.getErrors().size());
        return result;
    }
}
```

- `this::updateProgress` подходит под `ProgressListener (long, long)`, а `this::isCancelled` —
  под `BooleanSupplier`. Так бэкенд получает прогресс и отмену от JavaFX, не завися от JavaFX.
- `call()` выполняется в фоновом потоке, поэтому внутри нельзя трогать GUI. GUI обновляется
  в `setOnSucceeded`, это делает фронт.
- Загрузку отменяют обычным `Task.cancel()`. Задача сразу становится `CANCELLED`, загрузчик
  на следующей строке видит `isCancelled()` и выходит. Данные при этом грузились в отдельное
  хранилище, его просто выбрасывают — точное число загруженных строк не нужно.

### 11.2. Мягкая остановка: `StoppableTask` и генерация

```java
public abstract class StoppableTask<T> extends Task<T> {     // StoppableTask.java, строки 5–16
    private volatile boolean stopRequested;

    public void requestStop() {
        stopRequested = true;
    }

    protected boolean shouldStop() {
        return stopRequested || isCancelled();
    }
}
```

```java
public record GenerationResult(int added, int requested) {   // GenerationResult.java
    public boolean stopped() {
        return added < requested;
    }
}
```

```java
@Override
protected GenerationResult call() {                         // GenerateContactsTask.java, строки 26–33
    updateMessage("Генерация " + count + " контактов");
    int added = generator.generateInto(target, count, this::updateProgress, this::shouldStop);
    GenerationResult result = new GenerationResult(added, count);
    updateMessage(result.stopped() ? "Остановлено, добавлено " + added : "Добавлено " + added);
    return result;
}
```

**Зачем это нужно.** Генерация пишет прямо в рабочее хранилище, и после остановки нужно
честно сказать, сколько добавлено. В первой версии «Отмена» вызывала `Task.cancel()`, а
число считалось в GUI как `store.size() - before`. Проблема: после `cancel()` задача сразу
переходит в `CANCELLED` и вызывает `onCancelled`, а фоновый поток в этот момент может ещё
дописывать текущий контакт. Число получалось «примерно», то есть результат зависел от
того, кто успеет первым (гонка).

Теперь отмена генерации **кооперативная**:

1. `requestStop()` только ставит флаг.
2. Генератор на следующей итерации видит `shouldStop() == true` и выходит из цикла.
3. `call()` **завершается нормально** и возвращает `GenerationResult` с точным `added` —
   его посчитал сам поток, который вставлял.
4. GUI получает результат в `onSucceeded` и проверяет `result.stopped()`.

- `volatile` нужен, чтобы флаг, выставленный в FX-потоке, гарантированно увидел фоновый поток.
- `shouldStop()` учитывает и `isCancelled()`, поэтому обычный `cancel()` тоже остановит
  генерацию (например, при закрытии окна).

## 12. Асимптотика (таблица для отчёта)

L — длина ключа, P — длина префикса, σ — число детей у узла (в именах обычно 1–30),
k — сколько вернуть, m — узлы, пройденные при сборе k значений, N — число узлов,
K = min(узлов в поддереве, maxNodes), D — глубина снимка.

| Операция | Сложность | Обоснование |
|---|---|---|
| `add` / `tryAdd` / `put` | O(L·log σ) | L шагов спуска, на каждом бинарный поиск ребёнка; сдвиг массива детей O(σ) — σ мало; подъём по `parent` O(L) |
| `findByKey` / `get` | O(L·log σ) | тот же спуск |
| `removeByKey` | O(L·log σ) | спуск + подъём O(L) + срезка не больше L узлов |
| `update` | O(L·log σ) | две проверки + удаление + вставка |
| `countByPrefix` | O(P·log σ) | спуск к узлу префикса, ответ уже лежит в `subtreeSize` |
| `findByPrefix` | O(P·log σ + m) | спуск + обход до набора k значений |
| `toArray` | O(N) | обход всего дерева |
| `snapshot` | O(K·D) | обход в ширину до лимита; для каждого узла строится строка-префикс длиной до D и проверяется `startsWith` |
| `clear` | O(1) | новый корень, старое дерево соберёт GC |
| `size` | O(1) | `root.subtreeSize` |
| Память | O(сумма длин ключей) | в худшем случае один узел на символ; общие префиксы хранятся один раз |

Загрузка CSV — O(размер файла): один проход (в первой версии было два).

## 13. Замеры (`Benchmark`)

Среднее по 5 прогонам после прогрева JIT. Данные — сгенерированные контакты с одинаковым seed.
Замеряется `TrieStore` (вместе с блокировками). Для `TreeMap` ключ нормализован так же,
подсчёт по префиксу — `subMap(p, p + Character.MAX_VALUE).size()`.

| N | Операция | Trie, мс | TreeMap, мс |
|---|---|---|---|
| 10⁴ | вставка 10⁴ | ≈ 24 | ≈ 8 |
| 10⁴ | поиск 10⁴ | ≈ 12 | ≈ 8 |
| 10⁴ | автодополнение ×1000 | ≈ 1.4 | ≈ 0.7 |
| 10⁴ | подсчёт в поддереве ×1000 | **≈ 0.12** | ≈ 5.4 |
| 10⁴ | удаление 10⁴ | ≈ 15 | ≈ 8 |
| 10⁵ | вставка 10⁵ | ≈ 224 | ≈ 116 |
| 10⁵ | поиск 10⁵ | ≈ 164 | ≈ 119 |
| 10⁵ | автодополнение ×1000 | ≈ 0.6 | ≈ 0.7 |
| 10⁵ | подсчёт в поддереве ×1000 | **≈ 0.08** | ≈ 310 |
| 10⁵ | удаление 10⁵ | ≈ 185 | ≈ 130 |

Эти цифры сняты на первой версии. После исправлений поиск стал немного дешевле (он больше не
пишет в узлы), так что перед отчётом обязательно запустите `Benchmark` у себя и вставьте свои
цифры: они зависят от компьютера.

**Как объяснить результаты:**

- **Вставка, поиск и удаление у Trie в 1.5–3 раза медленнее.** `TreeMap` делает около
  log₂(10⁵) ≈ 17 сравнений строк, и сравнение обычно обрывается на первых буквах. Trie делает
  шаг на **каждый** символ имени (около 25) с бинарным поиском в узле и создаёт много мелких
  объектов. Это плохо для кэша процессора и нагружает GC.
- **Подсчёт в поддереве у Trie в тысячи раз быстрее,** и разрыв растёт с N. У Trie ответ лежит
  в узле, O(P). У `TreeMap` `subMap(...).size()` проходит все элементы диапазона, O(log n + k).
- **Автодополнение примерно равное.** Оба находят начало диапазона и берут первые 10.

Вывод: Trie выигрывает там, где важна работа с префиксами, для этого он и выбран в варианте.

## 15. Сводка архитектурных решений

| Решение | Альтернатива | Почему так |
|---|---|---|
| Дети — сортированные массивы + бинпоиск | массив на алфавит, список, HashMap | память по факту, O(log σ), алфавитный порядок без сортировки |
| `subtreeSize` в каждом узле | считать обходом | подсчёт по префиксу за O(P), а не O(поддерева) |
| Ссылка `parent` в узле | стек пути при спуске | простой подъём для счётчиков и срезки |
| Срезка пустых веток при удалении | оставлять пустые узлы | дерево не растёт от вставок-удалений |
| Ключ — имя в нижнем регистре | имя как есть | поиск и автодополнение без учёта регистра |
| Обобщённый `Node<V>` | `Object value` + приведения | проверка типов компилятором, нет приведений при чтении |
| Неизменяемые контакты + `withName` | сеттеры | ключ в дереве не может поменяться в обход хранилища; безопасно между потоками |
| `add` бросает, `tryAdd` возвращает `false` | только `boolean` | пользователю нужна понятная ошибка, массовым операциям — дешёвая проверка |
| Разные исключения в `update` | `boolean` | GUI показывает правильную причину; в лабе 5 — 404 и 409 |
| Подсветка через `highlightKey` в снимке | `stamp` в узлах | чтение без побочных эффектов, подсветку не перебивают другие операции |
| Снимок `TrieNodeView` (record) | отдать GUI сами узлы | инкапсуляция, GUI не испортит дерево |
| Снимок с лимитом, обход в ширину в массивы | весь снимок, рекурсия | быстро даже на 10⁵, видны верхние уровни, сборка одним циклом |
| `Trie` без синхронизации, `TrieStore` с ней | синхронизировать сам `Trie` | структура и потокобезопасность — разные ответственности; можно показать гонку |
| `ReentrantReadWriteLock` | `synchronized` на всём | читатели работают параллельно; стало возможно, когда чтение перестало писать |
| CSV с кавычками (`CsvFormat`) | `split(";")` | `;` и `"` в данных не ломают файл |
| Прогресс в байтах (`CountingInputStream`) | сначала посчитать строки | один проход по файлу вместо двух |
| `StoppableTask` + `GenerationResult` | `Task.cancel()` и разница размеров | точное число добавленных, без гонки |
| Интерфейсы `EntityStore` / `PrefixStore` | работать с `TrieStore` напрямую | CSV и GUI не зависят от реализации; готовность к Spring |
| `ProgressListener` + `BooleanSupplier` | передавать `Task` в загрузчик | бэкенд не зависит от JavaFX, тестируется без GUI |
| Результаты — массивы | `List` | ограничение лабы на списки |
| `TreeMap` только в `src/test` | в основном коде | требование: аналог из java.util только для эксперимента |

## 17. Как пользоваться бэкендом из кода

```java
TrieStore<Contact> store = ContactStores.create();

store.add(new Contact("Иван Петров", "+7913", "ivan@mail.ru", "НГТУ"));
boolean added = store.tryAdd(new Contact("иван петров", "", "", ""));        // false — дубликат
try {
    store.add(new Contact("иван петров", "", "", ""));
} catch (DuplicateKeyException e) {
    System.out.println("Уже есть: " + e.getKey());
}

Contact c = store.findByKey("ИВАН ПЕТРОВ");                                 // найдёт
Contact[] hints = store.findByPrefix("ив", 10);                             // автодополнение
int n = store.countByPrefix("ив");                                          // подсчёт
store.update("Иван Петров", c.withName("Иван Сидоров"));                    // переименование
store.removeByKey("Иван Сидоров");

LoadResult r = new CsvLoader().load(Path.of("test.csv"), store);           // загрузка
new CsvSaver().save(Path.of("out.csv"), store);                            // сохранение
new ContactGenerator(42).generateInto(store, 10_000);                      // генерация

TrieNodeView view = store.snapshot("ив", 20, 200, "Иван Петров");          // для рисования
System.out.print(TriePrinter.print(view));                                 // или в консоль
```

`load` и `save` бросают `IOException`, его нужно обработать или пробросить. В выводе
`TriePrinter` подсвеченные узлы помечены `*`.

## 18. Вопросы по бэку на защите

- **Почему Trie, а не просто отсортированный массив?** Так задано вариантом. По существу Trie
  даёт подсчёт по префиксу за O(P) и автодополнение без бинарного поиска границ. Общие префиксы
  («Иванов …») хранятся один раз.
- **Что будет, если у двух контактов одинаковое имя?** Второй не добавится: `add` бросит
  `DuplicateKeyException`, `tryAdd` вернёт `false`, а CSV даст `DUPLICATE_NAME`. Ключ
  уникален, как первичный ключ в БД.
- **Зачем и `add`, и `tryAdd`?** `add` — для действий пользователя, где дубликат надо
  показать как ошибку. `tryAdd` — для загрузки и генерации, где дубликат — обычное дело и
  исключение на каждый повтор не нужно.
- **Почему `update` бросает исключения, а не возвращает `false`?** У неудачи две разные
  причины: старого контакта нет или новое имя занято. С `boolean` их не различить, и GUI не
  может сказать пользователю, что случилось. С исключениями — может, и ещё получает ключ
  через `getKey()`.
- **Почему контакты неизменяемые?** Контакт лежит в дереве под своим именем. Если бы имя
  можно было поменять сеттером, объект остался бы под старым ключом и перестал бы находиться.
  Теперь изменить можно только через `withName` + `store.update`. Плюс неизменяемые объекты
  безопасно читать из разных потоков.
- **Почему `get("ива")` возвращает null, хотя узел есть?** Узел есть, но значения в нём нет:
  имя «ива» не добавлялось, это только часть «иван».
- **Как работает `-(lo + 1)` в бинарном поиске?** Если элемент не найден, `lo` — позиция, куда
  его вставить. `+1` нужен, чтобы позиция 0 не совпала с «найдено в 0»: результат всегда
  отрицательный. Позиция восстанавливается как `-(i + 1)`.
- **Сколько стоит расширение массива детей?** O(σ) при удвоении. Амортизированно это O(1)
  на вставку ребёнка: удвоения редки, как в `ArrayList`.
- **Зачем `parent`?** Чтобы после вставки или удаления подняться к корню и поправить
  `subtreeSize`, и чтобы срезать пустую ветку снизу вверх.
- **Почему `new T[n]` нельзя, а `Contact[]::new` можно?** Из-за стирания типов `T` в рантайме
  неизвестен. Ссылка на конструктор массива — обычная функция, которая знает конкретный тип.
- **Зачем `@SuppressWarnings("unchecked")`, если узел обобщённый?** Нельзя создать массив
  `new Node<V>[n]`. Создаётся `new Node[n]` и приводится в одном месте (`newNodes`). Значения
  при этом читаются без приведений.
- **Как теперь работает подсветка?** Дерево ничего не помечает. В снимок передаётся
  `highlightKey`, и узел подсвечен, если этот ключ начинается с префикса узла.
- **Что если убрать блокировки?** Теряются вставки, `size()` врёт, бывают
  `ArrayIndexOutOfBoundsException`. Это показывает `RaceDemo`.
- **Зачем блокировка чтения, если чтение ничего не меняет?** Чтение не меняет, но может
  идти одновременно с записью, которая сдвигает или пересоздаёт массивы детей. Блокировка
  чтения не пускает писателя, пока читают, но не мешает читателям друг другу.
- **Почему раньше нельзя было `ReadWriteLock`?** Поиск и автодополнение писали `stamp` и
  `visitStamp` в узлы. Два «читателя» под общей блокировкой чтения гонялись бы на этих полях.
  Когда подсветку перенесли в снимок, чтение стало чистым, и `ReadWriteLock` стал корректным.
- **Как считается прогресс загрузки?** В байтах: `CountingInputStream` считает прочитанные
  байты, общий объём — `Files.size(file)`. Файл читается один раз. Раньше строки считались
  отдельным проходом, это почти удваивало время на большом файле.
- **Что будет, если в названии организации есть `;`?** При сохранении поле берётся в кавычки,
  при загрузке `CsvFormat.split` понимает кавычки. Если кавычки в файле сломаны — строка
  пропускается с кодом `BAD_QUOTES`.
- **Как проверяется отмена?** Загрузчик и генератор получают `BooleanSupplier` и проверяют
  его на каждой итерации цикла. Из `LoadCsvTask` туда передаётся `this::isCancelled`, из
  `GenerateContactsTask` — `this::shouldStop`.
- **Почему генерацию останавливают через `requestStop`, а не `cancel`?** После `cancel()`
  задача сразу считается отменённой, а фоновый поток ещё может вставлять. Число добавленных,
  посчитанное в этот момент в GUI, неточное. При `requestStop` поток сам выходит из цикла и
  возвращает точное `added` в `GenerationResult`.
- **Где используются списки и почему это можно?** `LoadResult` хранит ошибки загрузки в
  `List`, `Editable.validate()` возвращает `List<String>`, `CsvFormat.split` собирает поля
  строки во временный `List`. Это вспомогательные данные, а не хранилище контактов. Контакты
  лежат только в `Trie`.
